# 動かすときの前提と、handler を書く人への契約

この基盤が**何を守り、何を守らないか**。守らないことは呼び出す側・書く側が引き受ける。

## 同じ DB を使う実行ホスト（Web）は 1 つだけ

**2 つ目を立ててはいけない。** 立てると、走っている Job が黙って閉じられる。

理由は起動時復旧にある。Web は起動のたびに、静止していない Job
（`InProgress` と確定待ちの `Pausing` / `Cancelling` / `Resuming`）を
「前回のプロセスが落ちて残した死骸」とみなして閉じる。確定待ちは要求どおりの行き先へ落とし、
`InProgress` だけは結果が分からない以上 `Failed` にするしかない。この判断は
**そのプロセスが唯一の実行者だった**ことを前提にしている。1 つ目が実際に実行している最中に
2 つ目を起動すると、2 つ目の復旧が 1 つ目の仕事を死骸と誤認する。

これは仕組みでは止めていない。守るのは運用の側。

- 同じ `Jobs__DatabasePath` を指す Web を 2 つ起動しない
- 開発中に「もう 1 つ立てて試す」ときは、DB のパスを分ける
- 落ちたかどうか怪しいときは、先にプロセスを確認してから起動する

### 復旧は API の受付より前に終わる

「唯一の実行者だった」という前提には、**API も書き手である**という続きがある。
利用者が実行中の Job を編集すると状態は動かないまま版だけが進むので、それが復旧の
書き戻しとぶつかると、その Job は `InProgress` のまま誰にも閉じられなくなる
（エンジンは待ち行列（`Registered` / `Resumed`）しか拾わず、キャンセルは `Cancelling`、
一時停止は `Pausing` で固着し、復旧はそのプロセスで二度と走らない）。

そこで復旧は HTTP の受付が始まる前に済ませてある（`JobExecutionHostedService.StartingAsync`）。
**起動処理を軽くしたくなっても、復旧を受付の後ろへ動かしてはいけない。**
待つのは高々 1 行の UPDATE で、非終端で残る Job は異常終了 1 回につき 1 件しか作れない。

### 「同時実行数は 1」とは別の話

README の「同時に走る Job は 1 つ」は**エンジンのループが 1 本**という意味で、
同時に処理する Job の数の話。こちらは**プロセスの数**の話で、根拠も別（前者はディスパッチの
設計、後者は復旧の前提）。片方だけ読んで安心しないこと。

### 複数プロセスにしたくなったら

Job に実行の所有権（worker の識別子と期限）を持たせ、復旧の対象を
「`InProgress` かつ期限切れ」に変える必要がある。期限を延ばすには定期的な書き込みが要るので、
いま持っている「アイドル時は 1 回も起きない」という性質と引き換えになる。
**必要になってから**やる。

なお、条件付き更新（版によるガード）は既に複数プロセスでも二重実行を防ぐ。
足りていないのは復旧だけで、そこだけが単一プロセス前提になっている。

## キャンセルと一時停止は、止まる場所が違う

同じ「止める」でも、要求の伝わり方は同じ ── **どちらも Job の状態として書かれ、
走っている handler が読みに来る**。違うのは<b>どこで効くか</b>だけ。

| | 伝え方 | 効くまで | プロセスをまたぐか |
|---|---|---|---|
| キャンセル | Job の状態を handler が読む | handler の観測点まで | **またぐ** |
| 一時停止 | Job の状態を handler が読む | 次の安全な境界まで | **またぐ** |

キャンセルが細かい粒度で効いてよいのは、**残りを捨ててよいから**。一時停止が境界まで
待つのは、途中で抜けると再開時にそのサブタスクを頭からやり直すことになるから
（サブタスクの状態に「途中まで」が無い）。粒度の差は仕掛けの差ではなく、意味の差。

かつてキャンセルだけは `CancellationToken` で伝えており、そのために「今どの Job が走っていて、
そのトークンはどれか」をプロセス内に覚える入れ物が要った。効きは即座だが、伝達が
同一プロセスに限られ、その入れ物がエンジンのループと HTTP のスレッドが同時に触る唯一の物に
なっていた。読みに来る形に揃えて、入れ物ごと消してある。

上の表は**実行中**の Job の話。待ち行列（`Registered` / `Resumed`）と `Paused` には
そもそも handler が居ないので、受理を待つ相手も居らず、要求を受けたコマンドが
その場で確定まで書く。**それでも要求は必ず一度は状態に残る**
（`Registered` → `Pausing` → `Paused`）── 押した事実が変更通知に流れないと、
画面から見て「押したのに何も起きていない」と区別が付かないため。

**待ち行列の 2 状態で受け付ける操作は同じ**で、分かれているのは登録直後
（`Create` でしか作られない）と一時停止から戻ってきたものを区別するため。

保留した Job は再開すると待ち行列へ戻る（`Paused` → `Resuming` → `Resumed`）ので、
**「まだ走らせたくない」を消さずに表せる**。キャンセルは終端で戻せないから、
「消す」と「いまは走らせない」は別の操作として要る。

## Pause 対応の handler を書く人への契約

**基盤が持つのは状態だけで、再開できるかどうかは handler の設計責任。**
`Paused` から `Resume` すると、基盤は Job を `Resuming` を経て `Resumed` へ戻し、**同じ handler をもう一度
最初から呼ぶ**。「続きから」に見せているのは handler 側であって、基盤ではない。

### 4 つの決めごと

**1. 安全な境界を自分で決める。**
仕事を、途中で止まっても困らない単位に割る。境界は「ここまでは終わったと言い切れる」点。
`SubTaskJobHandler` はサブタスク 1 個の完了を境界にしている。

**2. 境界で Job の状態を読み、`Pausing` なら `JobPausedException` を投げる。**
基盤は handler を勝手に中断しない ── `CancellationToken` は渡らない。
読みに行かない handler は永久に止まらない。

```csharp
Job? job = await _jobs.FindAsync(jobId, CancellationToken.None);
if (job?.Status == JobStatus.Pausing)
{
    throw new JobPausedException(jobId);
}
```

投げた後は基盤が `Paused` を書く。途中まで進めた分を捨てる必要はない ── むしろ
**捨ててはいけない**（次の 3 の前提が崩れる）。

**3. どこまで済んだかを、自分で永続化する。**
基盤は「どこまで進んだか」を一切覚えていない。覚えているのは Job の状態だけ。
`SubTaskJobHandler` はサブタスクの行を DB に持ち、その行の状態が checkpoint そのものになる。

**4. 再開時は、済んだ分を読み飛ばす。**
handler の入口は毎回同じ。前回の続きにするのは、永続化した記録を読んで
「終わっているものは飛ばす」を自分で書くから。

### ついでに満たしておくこと

- **キャンセルにも応じる。** 同じ読みで `Cancelling` も見て、`JobCancelledException` を投げる。
  観測点は一時停止の境界より細かくてよい ── 残りを捨てるので、区切りまで待つ理由が無い。
  **長く待つ処理を持つなら、待ちを刻んでその都度読むこと。**気づくまでの時間は、
  読みに来る間隔そのものになる（`SubTaskJobHandler` は 1 秒の待ちごとに 1 回）
- **同じ入力で何度呼ばれてもよい形にする。** 再開のほか、条件付き更新の競合でも
  handler が呼び直されうる
- **編集（parameters の差し替え）は境界で読み直す。** 実行中に変わりうる。
  読み直さない handler は、編集を無視するという選択をしたことになる（それでもよい）

### 対応しないという選択

Pause を実装しない handler があってもよい。その場合は境界で状態を読まなければよく、
一時停止の要求は `Pausing` のまま宙に浮いて、Job が終わるまで受理されない。
**中途半端に対応するより、しないほうがまし**（`Paused` と表示されているのに
実は続きから走れない、が最悪）。
