# ビルド・テスト・カバレッジ

```bash
dotnet build
dotnet test
dotnet format            # CI では --verify-no-changes で検査される
tools/coverage.sh        # 計測 → マージ → 基準判定。CI の Test はこれ

tools/gate.sh            # build / coverage.sh / format をコミットした木で通し、push を解錠する
```

`tools/gate.sh` を通していないコミットは push できない。止めるのは 2 つで、
`tools/gate-hook.sh`（コマンドの実行前）と `tools/git-hooks/pre-push`（押す直前）。
後者は `tools/gate.sh` が `core.hooksPath` を貼るので、一度通せば入る。
手順ごと通すなら `/ship` を使う。

**.NET 10 SDK が必要**（`global.json` で固定）。ターゲットは `net10.0`、C# 14。

## カバレッジの規則

- 基準は **C1（ブランチ）80% を src の各プロジェクトが個別に**満たすこと。下回ると CI が落ちる。
  行（C0）は計測・表示されるが基準にはしない。分岐を全部通せば行はほぼ付いてくるので、
  行の基準は「行を踏むだけで判断を検証しない」テストを温存する圧力にしかならない
- **合算ではなくプロジェクトごとに当てる**。合算だと分岐の多い
  プロジェクトが基準を押し上げ、小さいものが素通りする（Domain 54 分岐に対し Contracts は 2）
- 計測そのものは全プロジェクトの結果をマージしたもので測る。テストは層をまたいで書かれており
  （Web の結合テストが Features のハンドラを、Features のテストが Domain を通す）、
  テストプロジェクト単位で測り直すと実際には検証されているコードが未カバーに見える。
  **当て方だけがプロジェクト単位で、計測は横断のまま**
- 実績値は目標ではない。基準を超えていれば下がってよい。**数字を維持するためにテストを書かない**
- **各テストプロジェクトは自分のファイルに書く**（coverlet.collector）。マージと判定は
  全部終わってから `tools/coverage.sh` が一度だけ行う。どの順で走っても、何本並列でも
  結果は変わらないので、`.slnx` の並び順にもテストプロジェクトの数にも縛られない
- **判定は「全部そろった後に一度だけ」でなければ成立しない。** カバレッジはプロジェクトを
  またいで積み上がるので、途中で当てると偽の赤になる（`Contracts` は tests/Web が走るまで
  分岐 0%。その分岐は Web の結合テストでしか通らない）
- **src にあるのにレポートへ現れないアセンブリは落とす。** 「0% だった」ではなく
  「誰も通していない」なので、欠けていること自体を検出する（`tools/coverage-check.py`）
- 設定は `coverage.runsettings`（計測と除外）と `tools/coverage-check.py`（基準）

  かつては coverlet.msbuild の `MergeWith` で 1 つの json に積み上げ、最後に走る
  tests/Web が判定していた。coverlet はその形では `-m:1`（直列）を要求しており、
  実測で 2 倍遅かった（44〜52 秒 → 23〜28 秒）。順序が判定の正しさを支えているのが弱点で、
  実際に一度壊れている。
- 除外してよいのは「E2E が実プロセスで検証しているが coverlet が計測できないもの」だけ。
  テストを書けるものを除外で隠さない

## テストの後始末

一時ファイルを使うテストはこの形にそろえる。同じ注意書きを各ファイルに写さず、ここを参照する。

- **一時ディレクトリはインスタンスごとに分ける**（`Path.GetRandomFileName()`）。
  xUnit はクラスをまたいで並行に走るので、固定名だと別のテストと同じファイルを掴む
- **SQLite のプールは自分の DB だけ閉じる**。`SqliteConnection.ClearPool(自分の接続文字列)` を使う。
  `ClearAllPools` は<b>プロセス全域</b>に効き、並行して走っている他のテストが使用中の接続まで
  破棄して `ObjectDisposedException` のフレークを起こす（実際に起きた）。
  接続文字列は store 側と同じ組み立て（`DataSource` のみ）にする。違うと別のプールに当たって効かない
- プールを閉じるのは削除の前。接続を握ったままだとファイルが開いたままで、Windows では削除に失敗する
- **後始末の失敗でテストの結果を変えない**。`IOException` は握りつぶす。一時ディレクトリはいずれ OS が回収する
