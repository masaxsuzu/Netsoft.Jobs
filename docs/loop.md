### 読み取り

- **`needs-review` の基準は効いた。** 付く割合は **#1〜#67 で 46%（31/67）、
  #68 以降で 33%（6/18）**。#68 で 3 つの条件に絞ってから、実際に絞れている。
  効き方の差も開いた ── 付いた PR は中央値 8 分、付いていないものは 2 分（直近 20 件では 12 分と 2 分）
- **GitHub 上のレビューが初めて付いた。** #85 に 3 件、いずれもコードを直させる指摘だった
  （破棄の保証・回収の確認・規則の置き場）。全体では 1 / 37 件。
  前回「レビューを呼ぶ仕組みはどこにも無い」と書いたが、**「稀に起きる」が正しい**。
  主な効き方が「auto-merge を保留して手を止める」であることは変わらない
- **マージまでの中央値（直近 20 件）が 2 分 → 6 分。悪化ではない。**
  伸ばしているのは #78 (333 分・GitHub Actions の障害)、#85 (85 分・レビューの往復)、
  #77 (84 分)、#76 (72 分・どちらも CI の修正)。**止まるべきものが止まっている**
- **テンプレート充足は直近 100% を維持。** #71 で push を機械で止めた効果が続いている
- **実測の記載は 79% → 81%（直近 80% → 90%）。前回の「効いていない側の候補」から外す。**
  直近 20 件で欠けているのは #69 と #81 の 2 件だけで、どちらも規約とスキルの文書しか
  変えていない PR ── 書く数字が無い。実質は 18/18

### この回で試して、入れなかったもの

**手戻り率を測ろうとして、機械的に定義できないと分かった。**
#83 → #84 → #85 が同じ場所を 3 回作り直しており、そこに指標が要るように見えた。

2 通り試した。「24 時間以内に同じ src ファイルを別 PR が触ったか」で **82%**、
「先の PR が書いた行を後の PR が消したか」で **132%（延べ）**。どちらも全部に当たる。

分けたかったのは「続きの作業」と「前の判断を捨てた作り直し」だが、
**差は差分の形に現れない**。#47 → #64 で 66 行消えているのは機能の続きで、
#83 → #84 で 18 行消えているのは判断の置き換え。区別は意図の側にしかない。

**全部に当たる指標は、0 のまま動かない指標と同じで何も選別しない**
（前回の「`needs-review` の的中」と同じ失敗の裏返し）。入れずに、
測ろうとした事実だけをここに残す。

### この回で直した規則

**無し。** 効いていない規則が見つからなかった。前回「候補」とした実測の記載は動いており、
テンプレート充足と `needs-review` はどちらも効いている。

数字を良く見せるためだけの変更はしない、という約束をここでも守る
（docs/build.md のカバレッジと同じ考え方）。
