# 設計判断記録 (ADR)

[Job Execution Engine 設計書](./job-execution-engine.md) で採用した判断のうち、後から「なぜこうなっているのか」を問われうるものを記録する。

各項目は「文脈 / 決定 / 根拠 / 却下した代替案 / 帰結」で構成する。

---

## ADR-001: 単一プロセス構成にする

**文脈**
Windows ワークステーション 1 台、利用者 1 人、クラウド利用なし。Job は数秒〜数時間。

**決定**
Web API・push 配信・Job 実行・永続化をすべて 1 つの ASP.NET Core プロセスに載せる。Job は同一プロセス内で実行する。

**根拠**

- プロセス分割 (Web と Worker の分離) は、複数ホストへのスケールや障害分離が目的。今回はどちらも要件にない。
- 分割すると、Web ⇄ Worker 間の IPC、双方の起動順序、片方だけ落ちた場合の整合が新たな課題として発生する。得るものがないのに複雑さだけ増える。
- 単一プロセスなら、制御コマンドから実行中ハンドルへのシグナル送出がメモリ上の操作で済む (§5.2)。これが Pause/Cancel の低レイテンシに直結する。

**却下した代替案**

- *Windows サービス + UI プロセスの分離*: サービス化するとインストール・権限・更新の手間が増える。単一利用者が自分の PC で使う道具としては過剰。
- *Job ごとに別プロセス*: 障害分離は得られるが、進捗・ログ・制御をすべて IPC 越しにする必要があり、`IJobExecutionContext` の設計が一気に重くなる。

**帰結**

- Job 実装のバグ (未処理例外・メモリリーク) がホスト全体を巻き込みうる。→ `JobRunner` で必ず例外を捕捉し、`Failed` に写像する。
- 将来プロセス分離が必要になったら `IJobDispatcher` の差し替えで対応する。ただし `IJobExecutionContext` の IPC 実装が最大の作業になることは認識しておく。

## ADR-002: Pause / Cancel を協調的中断で実現する

**文脈**
実行中の Job を安全に止めたい。Job の中身はエンジンから見て不透明。

**決定**
`Thread.Abort` / `Thread.Interrupt` / タスクの強制終了は一切使わない。`IJobExecutionContext.CheckpointAsync()` を Job 実装が明示的に呼び、そこでのみ停止・中断が起きる。

**根拠**

- Job は装置制御・ファイル書込・外部通信を行いうる。任意の地点で強制中断すると、ファイルが半端な状態で残る、装置が不定状態になるなど、回復不能な副作用が生じる。
- .NET では `Thread.Abort` はそもそも .NET Core 以降サポートされない (`PlatformNotSupportedException`)。技術的にも選択肢ではない。
- 要件が「停止は即時ではなく、安全な停止地点で反映される」と明示している。設計はこれを型として表現すべき。

**却下した代替案**

- *Job ごとに別 `AppDomain` / プロセスにして強制終了*: 強制終了できても外部副作用は巻き戻らない。問題を解決しない。

**帰結**

- Checkpoint を呼ばない Job は止まらない。→ Job 実装ガイドで「ループの先頭で必ず呼ぶ」を規約化し、`FakeJobExecutionContext` で検証可能にする (§11.2b)。
- `Pausing` / `Cancelling` という過渡状態が必要になる。これは UI にとってもむしろ正しい表現 (「停止要求中…」)。

## ADR-003: Pause と Cancel を単一の `CheckpointAsync()` に統合する

**文脈**
Job 実装者は、キャンセル確認 (`ThrowIfCancellationRequested`) と一時停止待機 (`WaitIfPausedAsync`) の 2 つを呼ぶ必要がある。

**決定**
両者を `ValueTask CheckpointAsync()` 1 つに統合する。

**根拠**

- API を 2 つに分けると、Job 実装者は必ず片方を書き忘れる。「Cancel は効くが Pause が効かない Job」が量産される。
- 「安全な停止地点」という概念は 1 つであって、Pause 用と Cancel 用に 2 種類あるわけではない。API が概念に一致する。
- `ValueTask` により、要求がない通常時はアロケーションなしで同期的に返る。ホットループ内で呼んでも実害がない。

**却下した代替案**

- *`CancellationToken` だけで両方表現する*: Pause は「待つ」であって「やめる」ではない。トークンのセマンティクスに合わない。

**帰結**

- `CancellationToken` も併せて公開する必要がある (`await stream.ReadAsync(buffer, ctx.CancellationToken)` のように I/O へ渡すため)。Checkpoint は「自分で確認する地点」、トークンは「他人に預ける中断手段」と役割が分かれる。この違いを Job 実装ガイドに明記する。

## ADR-004: 状態遷移の入口を 1 箇所に集約する

**文脈**
状態を変える契機が複数ある: UI 操作、ディスパッチ、Checkpoint 到達、ハンドラ完了・例外、起動時復旧、シャットダウン。

**決定**
`IJobLifecycleCoordinator.TransitionAsync` を唯一の入口とし、遷移判断は純関数 `JobStateMachine.Evaluate` に委ねる。ロック取得 → 再読込 → 判定 → 更新 → 永続化 → (コミット後) イベント発行、の手順を Coordinator が保証する。

**根拠**

- 遷移が各所に散ると、「Paused から Cancel できない」「Cancel 中に Pause できてしまう」といった穴が必ずどこかに開く。
- 不変条件の守り手が 1 箇所にあると、テストもそこに集中できる (§11.3-1)。
- 「ロック内で永続化まで、通知はロック外」という規律を Coordinator が持つことで、呼び出し側がロック順序を意識しなくてよくなる。

**却下した代替案**

- *`Job` 集約のメソッド (`job.Pause()`) に遷移ロジックを置く*: ドメイン駆動としては自然だが、ロック・永続化・イベント発行との組み合わせを呼び出し側が毎回書くことになり、その部分で誤りが起きる。集約はデータと不変条件を持ち、手順の保証は Coordinator が持つ、と分ける。

**帰結**

- `JobRunner` や `StartupRecoveryService` も、直接 DB を書かず Coordinator を通す。例外はない。

## ADR-005: push は SignalR、状態の正は REST

**文脈**
数時間動く Job の進捗を、ブラウザで追随したい。

**決定**
参照・操作は REST、変化の通知は SignalR (WebSocket)。push は best-effort とし、再接続時は必ず REST で取り直す。

**根拠**

- ポーリングを主にすると、間隔が長ければ体感が悪く、短ければ無駄な負荷になる。長時間 Job の監視という用途に合わない。
- SignalR は ASP.NET Core 標準で、自動再接続・トランスポートのフォールバック・Group による購読分割が最初から入っている。SSE でも実現できるが、再接続とバックオフを自前で書くことになり差が消える。
- push に配信保証を持たせようとすると、outbox・ack・重複排除が必要になる。「REST が正」と割り切れば、これらがすべて不要になる。

**却下した代替案**

- *SSE (Server-Sent Events)*: 単一利用者なら十分成立する。SignalR より依存が軽い。→ SPA 側で SignalR クライアントを持ちたくない場合はこちらでもよく、その場合も §7.2 の「version 付き通知 + 再接続時に再取得」の設計はそのまま使える。
- *ポーリングのみ*: フォールバックとしては残すが、主方式にはしない。

**帰結**

- すべての通知に `version` を載せ、クライアントは古い通知を捨てる (順序逆転耐性)。
- ログは `sequence` 付きで配信し、欠番検知で増分取得できるようにする。

## ADR-006: 永続化は SQLite

**文脈**
Job の状態・履歴・ログを、プロセス再起動をまたいで保持する必要がある (UC9)。サーバ製品は導入したくない。

**決定**
SQLite (WAL モード) を単一ファイルで使う。アクセスは EF Core、またはクエリ性能が問題になる箇所のみ Dapper 併用。

**根拠**

- サーバ不要・単一ファイル・ACID。バックアップがファイルコピーで済む。
- UC9 の検索条件 (種別・状態・作成日時の組み合わせ) が SQL で素直に書け、インデックスで一定性能を保てる。
- クラッシュ耐性がある。異常終了時に「状態が壊れた DB が残る」ことを避けられるのが、JSON ファイル保存との決定的な差。

**却下した代替案**

- *JSON / CSV ファイル*: クラッシュ時の部分書込に耐えない。検索・ページングを自前実装することになる。
- *LiteDB*: 悪くないが、SQL の柔軟性・調査ツールの豊富さ・実運用実績で SQLite が優位。
- *SQL Server LocalDB*: 単一利用者のワークステーションに対して導入と運用が重い。

**帰結**

- 書込は直列化が必要 (§8.1)。進捗の高頻度更新はインメモリ集約 + 周期フラッシュで吸収する (§9.4)。
- 日時は UTC の ISO 8601 文字列で保存する (SQLite に日時型がないため)。

## ADR-007: 再実行は新しい Job を生成する (元 Job を書き換えない)

**文脈**
UC10。Retry 対応 Job のみ再実行できる。

**決定**
再実行は元 Job の状態を `Queued` に戻すのではなく、パラメータをコピーした**新しい Job** を作る。`RetryOfJobId` / `RootJobId` / `AttemptNumber` で系譜を辿れるようにする。

**根拠**

- 元 Job を書き換えると、1 回目の失敗理由・所要時間・ログが消える。UC8 (実行結果の確認) と UC9 (履歴) が成り立たなくなる。
- 「終端状態は不変」という規則が保てると、履歴データが後から変化しないことが保証され、状態機械も単純になる (終端からの遷移が一切ない)。
- 何回試行したか、各回で何が起きたかが自然に残る。

**却下した代替案**

- *同一 Job を再キューする*: 実装は単純だが履歴を失う。長時間 Job では「前回どこまで進んで落ちたか」が最も知りたい情報であり、これを消すのは致命的。

**帰結**

- UI に「試行 2 / 3」のような系譜表示と、`GET /api/jobs/{rootId}/attempts` が必要になる。
- 削除ポリシー (§9.5) は系譜単位で考える必要がある (親だけ消えて子が孤児にならないよう、`RootJobId` 単位で判定する)。

## ADR-008: 起動時、`Queued` の Job は `Failed` にせず `Queued` のまま残す

**文脈**
要件 5「アプリケーションまたは PC が異常終了した場合、実行中だった Job は失敗扱いとする。自動復旧・自動再開は含めない」。

**決定**
起動時の復旧走査で `Failed(ProcessTerminated)` にするのは `Running` / `Pausing` / `Paused` / `Cancelling` の 4 状態。`Queued` は `Queued` のまま残し、通常どおりディスパッチする。

**根拠**

- `Queued` の Job はハンドラが一度も呼ばれておらず、いかなる副作用も起こしていない。これを「失敗」と記録するのは事実に反する。
- 要件が禁じる「自動再開」は、**途中まで進んだ処理を勝手に続きから再開すること**を指すと解釈した。未着手のものを予定どおり開始するのは再開ではない。
- 利用者が作成した Job が、アプリを再起動しただけで理由なく失敗扱いになると、毎回作り直しになる。

**却下した代替案**

- *`Queued` も `Failed` にする*: 「異常終了時に何も自動で動かない」という点では最も保守的。ただし上記の実害がある。
- *`Queued` を残すが自動ディスパッチせず、利用者の明示操作で開始する*: 最も安全だが、`Queued` とは別に「保留」状態が必要になり状態機械が複雑化する。単一利用者・単一 PC の道具としては過剰。

**帰結**

- この判断は要件の解釈に依存する。装置制御など「作成時点と再起動後で前提が変わりうる Job」を扱う場合は方針が変わりうるため、**設定 (`RecoveryPolicy.QueuedJobs = Resume | Fail`) で切り替え可能にする**。既定は `Resume`。
- 起動時に「前回の異常終了により N 件の Job を失敗として記録しました」を UI に通知し、`Queued` の残件数も併せて示す。

## ADR-009: 同時実行数の既定値は 1

**文脈**
同時実行数をいくつにするか。エンジンとしては任意の値をとれる。

**決定**
既定 `MaxConcurrentJobs = 1`。設定で変更可能。加えて Job 型ごとの上限 (`JobTypeAttribute.MaxConcurrency`) を持てる。

**根拠**

- 対象は単一ワークステーションで、Job には装置制御やファイル I/O が含まれうる。並列化すると資源競合が起きやすく、しかもその競合は Job 実装者が予期しにくい。
- 直列なら「今動いているのはこれ」が自明で、UI・ログ・障害調査のすべてが単純になる。
- 並列化は後から設定値を上げるだけで有効化できる。逆 (並列前提で作って直列に戻す) は難しい。安全側から始める。

**帰結**

- 長時間 Job が 1 本走っている間、後続は `Queued` で待つ。UI で待ち順を見せる必要がある (一覧を作成日時順にすれば自然に満たせる)。
- Job 型ごとの上限があるため、「装置制御は常に 1 本、解析は 4 本並列」といった構成が全体設定と独立に表現できる。

## ADR-010: `availableOperations` をサーバが算出して返す

**文脈**
UI は Pause/Resume/Cancel/Retry ボタンの活性を制御する必要がある。判定材料は 能力 × 状態 × 保留要求。

**決定**
サーバが判定結果 (`availableOperations: ["cancel"]`) を DTO に載せて返す。UI は判定ロジックを持たない。`capabilities` (原理的な対応可否) は別フィールドとして併せて返す。

**根拠**

- 判定ロジックが UI とサーバの 2 箇所にあると、状態が増えたとき片方を直し忘れる。ズレると「押せるのに 409 になるボタン」ができる。
- サーバは同じ `JobStateMachine.AvailableOperations` を、API の検証とレスポンス生成の両方で使う。単一の真実が保てる。
- `capabilities` を分けて返すのは、「ボタン自体を出さない (Pause 非対応 Job)」と「ボタンは出すが今は押せない (実行中でないので Pause 不可)」を UI が区別するため。

**却下した代替案**

- *UI 側で状態から判定する*: 通信量は減るが、上記の二重管理を招く。DTO の数十バイトの方が安い。

**帰結**

- API 側は UI を信用せず、必ずもう一度検証する。`availableOperations` は UI の利便性のためであって、認可ではない。

## ADR-011: エンジンは Job パラメータの構造を知らない

**文脈**
Job ごとにパラメータの形が違う。DB にどう保存し、UI のフォームをどう作るか。

**決定**
DB には `ParametersJson` として生の JSON を 1 列で保存する。Job 型ごとのテーブルは作らない。UI のフォームは、パラメータ型から生成した JSON Schema をもとに自動構築する。

**根拠**

- Job 型ごとにテーブルを作ると、Job を 1 つ追加するたびに DB マイグレーションが必要になる。「エンジンを変更せずに Job を追加できる」という最重要の性質が壊れる。
- パラメータで検索する要件はない (UC9 の検索条件は種別・状態・作成日時のみ)。JSON のままで困らない。
- スキーマをコードから生成すれば、パラメータ型を変えたときにフォームが自動追従する。二重管理が発生しない。

**却下した代替案**

- *キー・バリューの縦持ちテーブル*: 型情報が失われ、ネストした構造を表現できない。
- *フォームを Job ごとに手書き*: 自動生成では表現できない UI (ファイル選択ダイアログ、依存する選択肢) は必要なので、**自動生成を既定としつつ、Job 型ごとにカスタムフォームを差し込める逃げ道を用意する**。

**帰結**

- パラメータ型を変更したとき、過去の Job の JSON は古い形のまま残る。詳細画面での表示は「保存された JSON をそのまま整形表示」を基本とし、再実行時はデシリアライズを試みて失敗したら理由つきで拒否する。

## ADR-012: 二重起動を禁止する

**文脈**
起動時復旧 (§5.3.4) は「非終端状態の Job = 前回の異常終了の残骸」という前提に立つ。

**決定**
名前付き Mutex で二重起動を禁止する。2 つ目のインスタンスは既存のブラウザ画面を開いて自身を終了する。

**根拠**

- 2 つ目のインスタンスが起動すると、1 つ目が正常に実行中の Job を「異常終了の残骸」と誤判定して `Failed` にしてしまう。実行中の処理を無関係なプロセスが失敗扱いにするのは、実害の大きいバグ。
- 加えて、2 プロセスが同じ SQLite ファイルに書き込み、同じ Job を二重にディスパッチしうる。

**却下した代替案**

- *プロセスインスタンス ID + ハートビート列で生存判定する*: 二重起動を許したまま復旧の正確さを保てるが、ハートビートの間隔・失効判定という新たなチューニング要素が増える。単一利用者の道具に対して割に合わない。

**帰結**

- 復旧処理と二重起動禁止は分離できない設計上の対であり、片方だけ実装してはならない。この依存関係をコード上のコメントとテストで固定する。
